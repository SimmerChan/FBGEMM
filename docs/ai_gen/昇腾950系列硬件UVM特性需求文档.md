### 1.3 根因：昇腾A5（当前 910 系列）缺乏 UVM 能力

> 🟢 A 类：表格中"NVIDIA 现状"列均有 CUDA 官方文档直接支撑（[CUDA Unified Memory Guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/04-special-topics/unified-memory.html)）。
>
> 🟡 B 类 + 🔴 C 类：**"昇腾 A5 现状 ❌ 不支持"列由 LLM 推断，无 CANN 8.0.x 官方文档一手核实**。需由 CANN 团队确认（A5 实际可能已部分支持）。

| UVM 能力 | NVIDIA 现状 | 昇腾 A5 现状 | 影响 | 可信度 |
|---|---|---|---|---|
| `cudaMallocManaged` 统一内存分配 | ✅ 成熟 | ❌ 不支持 | TBE 表无法"虚拟化" | 🟢 NVIDIA / 🟡 A5 |
| `cudaMemAdvise` hint | ✅ 6 种 advice | ❌ 不支持 | 无法声明数据归属 | 🟢 NVIDIA / 🟡 A5 |
| `cudaMemPrefetchAsync` 预取 | ✅ 成熟 | ❌ 不支持 | 无法主动搬运热点 | 🟢 NVIDIA / 🟡 A5 |
| `__managed__` 编译期 UVM 变量 | ✅ 支持 | ❌ 不支持 | 部分三方库依赖 | 🟢 NVIDIA / 🟡 A5 |
| `cuMemAllocManaged` (driver API) | ✅ 支持 | ❌ 不支持 | 低层级控制不可用 | 🟢 NVIDIA / 🟡 A5 |
| 跨卡 UVM (multi-GPU shared virtual addr) | ⚠️ 见下方澄清 | ❌ 不支持 | 集群扩展受限 | 🟢 NVIDIA 实际行为 / 🟡 A5 |

#### 1.3.1 关键语义澄清：`cudaMemAdvise` / `aclrtMemAdvise` 是 hint，**不是**访问控制

> ⚠️ **本小节是 2026-06-10 增补的关键澄清。** 表格中"跨卡 UVM (multi-GPU shared virtual addr) ✅ 支持"这一行的"NVIDIA 现状"容易让读者误以为 NVIDIA 提供了某种"跨卡 UVM 共享"机制。**实际不是这样**。

**`cudaMemAdvise` 的本质**：性能优化提示（hint），不是访问控制。

| 误解 | 真相 |
|---|---|
| "把 UVM 内存 advise 给卡 0 后，卡 1 就不能访问了" | ❌ 错。卡 1 **仍能访问**，只是不享受性能优化 |
| "advise 是访问控制" | ❌ 错。UVM 访问控制由 **OS 页表** 负责，与 advise 无关 |
| "不 advise 给卡 1，卡 1 访问会失败" | ❌ 不会失败，但每次访问都触发 **page fault** |

**6 种 advice 的语义分类**：

| Advice | 实际语义 | driver 收到 hint 后会做什么 |
|---|---|---|
| `SetPreferredLocation` | "这片内存的**家**在 X" | page fault 时**优先迁回 X**；避免乱迁移 |
| `UnsetPreferredLocation` | 解除上一条 | — |
| `SetAccessedBy` | "X device 将来要访问" | 预先在 X device 上建立 **direct mapping**，**避免 page fault** |
| `UnsetAccessedBy` | 解除上一条 | — |
| `SetReadMostly` | "只读热点" | 多 device 场景下**复制**到 X device 的 cache |
| `UnsetReadMostly` | 解除上一条 | — |

**对表格"跨卡 UVM"行的重新表述**：

⚠️ **"跨卡 UVM (multi-GPU shared virtual addr) ✅ 支持"应理解为**：
- NVIDIA **允许** 同一节点内多卡看到同一片 UVM 内存的**虚拟地址**
- 但需要每张卡都 `SetAccessedBy` 才会享受 direct mapping（零 fault）
- **没** advise 的卡访问时仍会 page fault
- **不**等于"一张卡能 zero-copy 读另一张卡的 HBM"
- 跨卡高性能访问仍需走 **`cudaDeviceEnablePeerAccess` + `cudaMemcpy` P2P** 或 **NCCL**

> 📌 **对昇腾 `aclrtMemAdvise` 的要求**：必须严格按 `cudaMemAdvise` 语义实现（hint 而非 access control），否则 FBGEMM 适配层会出错。

#### 1.3.2 FBGEMM 单卡边界的真正成因

FBGEMM 中 UVM 的"单卡"边界**不是被 CUDA 技术阻止**的，而是**被 FBGEMM 主动设计**出来的：

```cpp
// memory_utils.cu:202-227
gpuMemAdvise(ptr, size_bytes, cudaMemAdviseSetPreferredLocation, cudaCpuDeviceId);
gpuMemAdvise(ptr, size_bytes, cudaMemAdviseSetAccessedBy, current_device());
//                                                  ^^^^^^^^^^^^^^^
//                                                  永远只 advise 本卡
```

- **理论可能性**（FBGEMM 没用）：可以循环 N 次 `SetAccessedBy` 给同节点所有卡
- **FBGEMM 实际**：只 advise 本进程当前那张卡
- **结果**：本卡零 fault；其他卡每次 fault

> 💡 **重要启示**：昇腾 `aclrtMemAdvise` 行为**必须**与 `cudaMemAdvise` 一致（hint 而非 access control），且能被循环调用以让多卡都建立 mapping——即便 FBGEMM 当前不用，**其他三方库可能用**。

**🟡 直接后果**（逻辑推论）：

- FBGEMM 的 `EmbeddingLocation.MANAGED` / `MANAGED_CACHING` 在昇腾上无法启用（**逻辑推论成立**——若 A5 真无 UVM 支持，则 FBGEMM 的 MANAGED 路径确实走不通）
- 客户只能用 `EmbeddingLocation.DEVICE`（HBM 装不下）或 `HOST`（必须显式 memcpy，性能差）
- 互联网客户无法把 NVIDIA 上跑通的 FBGEMM 模型零修改迁过来

> **行动项**：见 §0.4 #6，**CANN 团队必须 M1 确认 §1.3 表格中"昇腾 A5 现状"的真实能力**（是否有任何 Managed Memory 雏形）。

### 1.4 战略价值：UVM 是打入搜广推市场的"入场券"

> 🟡 **2026-06-10 增补边界澄清**：UVM 在 FBGEMM 中**只有"单进程 / 单节点"半径**。跨节点（多机）embedding 访问由 TorchRec sharding + NCCL/HCCL all_to_all 解决，**与 UVM 完全无关**。详见 [FBGEMM_UVM分析报告.md §10](FBGEMM_UVM分析报告.md#10-uvm-在-fbgemm-中的边界澄清2026-06-10-增补)。

| 战略定位 | 说明 | 可信度 | 半径 |
|---|---|---|---|

## 2. 详细描述

### 2.1 目标硬件形态

> 🔴 **本节中三种形态的"典型部署规模"（4-16 卡、8-1024 卡）等数字均为 AI 推测，** 非华为官方产品手册。**硬件产品线需 M1 提供一手规格数据**。三者角色定位（标卡/服务器/POD）为 🟢 行业一般性认知。

| 形态 | 定位 | 典型部署规模 | 主要 UVM 价值 | 可信度 |
|---|---|---|---|---|
| **950PR 标卡** | 单卡 PCIe 加速器 | 1–2 卡/服务器 🔴 | 编程便利性、降低小规模推荐上线门槛 🟢 | 部署规模 🔴，角色 🟢 |
| **950DT 服务器** | 一体化 AI 服务器 | 4–16 卡/服务器 🔴 | **容量扩展**——把百 GB 级 embedding 表溢出到 CPU DRAM 🟢 | 部署规模 🔴，角色 🟢 |
| **950DT POD** | 大规模集群 | 8–1024 卡/POD 🔴 | 跨卡 / 跨节点统一内存，支持 TB 级 embedding 表 🟢 | 部署规模 🔴，角色 🟢 |

**三者关系**（🟢 行业一般性认知）：标卡是"易用性"主战场，DT 服务器是"容量扩展"主战场，DT POD 是"集群共享"主战场。**DT 服务器是搜广推场景的"主菜"**（互联网客户的主力部署形态），DT POD 是头部互联网客户的诉求，标卡是补全小客户覆盖。

### 2.2 需求总目标（一句话）

> **在昇腾 950PR / 950DT / 950DT POD 三种硬件形态上，提供与 NVIDIA CUDA UVM 功能对等、性能在 FBGEMM 用例场景下持平竞品的统一内存（UVM）能力**，使 FBGEMM / TorchRec 等三方库可"零修改"运行在昇腾 NPU 上，支撑搜广推业务场景。

- 仿照 FBGEMM `memory_utils.cu:202-227` 的两步 advise：`SetPreferredLocation=CPU` + `SetAccessedBy=GPU`，建立 direct mapping 避免 page fault
- 启用 2 MB 大页（Linux THP / CMA 配合），减少 30–50% fault 开销
- 与 HCCL 协同预取

#### 2.3.4 三个硬件形态的差异化规格

> 🟡 **2026-06-10 增补边界澄清**：950DT POD 行的"跨节点统一内存"中，**UVM 只覆盖"单节点内多卡"部分**；**跨节点（多机）emb 通信由 HCCL over RoCE/IB 解决，与 UVM 无关**。详见 [FBGEMM_UVM分析报告.md §10](FBGEMM_UVM分析报告.md#10-uvm-在-fbgemm-中的边界澄清2026-06-10-增补)。

| 维度 | **950PR 标卡** | **950DT 服务器** | **950DT POD** |
|---|---|---|---|
| **UVM 范围** | 单卡 host↔device | 单机 8 卡 host↔device↔device | **单节点内**多卡 host↔device↔device（POD 内每节点独立） |
| **统一虚拟地址空间** | host + 1 device | host + 8 devices | 每节点 host + 8 devices（POD 内**不**统一） |
| **page migration 路径** | PCIe Gen5 | PCIe Gen5 + 卡间高速互联 | 每节点内 PCIe + 卡间互联；**跨节点走 HCCL over RoCE/IB（与 UVM 无关）** |
| **典型 UVM 用例** | 小模型推理 + cache | 8 卡推荐训练 + 推理 | 每节点内 8 卡 UVM（与单服务器 DT 形态相同） |
| **功能要求** | P0 项 1-10 | P0 项 1-10 + 跨卡 advise | P0 + P1（**与 DT 服务器相同**；不新增跨节点 UVM 需求） |
| **性能基准** | 单卡 benchmark | `nbit_uvm_compare_direct_mapped` 8 卡 | 每节点 8 卡 benchmark（**与 DT 服务器相同**） |
| **典型客户场景** | 中小企业、广告小流量推理 | 互联网中等规模推荐 | 互联网头部大模型推荐（跨节点由 TorchRec + HCCL 解决） |

> ⚠️ **关于 950DT POD 的明确边界**：
> 1. **POD 形态不引入额外的 UVM 需求**——每节点内 UVM 行为与 950DT 服务器完全相同
> 2. **跨节点 embedding 同步**由 `torch.distributed.all_to_all_single` + `HCCL` over RoCE/IB 完成，**属于集合通信层而非 UVM 层**
> 3. POD 形态相比 DT 服务器的额外需求应放在 **HCCL 集合通信性能 / RoCE 网络 / NVMe 共享存储** 等产品线，**不**在 UVM 需求文档中

#### 2.3.5 编程接口需求

**目标**：使 FBGEMM / TorchRec 等三方库**"零修改"运行**。

实现路径：
- **路径 A（推荐）**：CANN 提供 `aclrtMallocManaged` / `aclrtMemAdvise` / `aclrtMemPrefetchAsync` 等 C/C++ API；FBGEMM-Ascend / TorchRec-Ascend 在 `memory_utils.cu` 中加宏开关，运行时检测 CUDA/CANN 分流
- **路径 B（兼容层）**：在 `fbgemm_gpu` 中增加 `cumem_utils_ascend.cc`，复用同一份 C++ 代码，把 CUDA API 替换为 CANN API

**接口规约（伪代码）**：
```cpp
// 950 DT/POD 必备
acldvppError aclrtMallocManaged(void** ptr, size_t size,
                                 unsigned int flags = 0);  // 0 = AttachGlobal
acldvppError aclrtMemAdvise(void* ptr, size_t count,
                              aclrtMemoryAdvise advice, int device);
acldvppError aclrtMemPrefetchAsync(void* ptr, size_t count,
                                    int dstDevice, aclrtStream stream);

// 950PR 简化路径
acldvppError aclrtMallocHostMapped(void** ptr, size_t size);  // 等价 cudaHostAlloc
```

### 4.2 现有方案的问题与缺陷

#### 4.2.1 推荐系统 embedding 表容量瓶颈

**问题**：客户推荐系统 embedding 表动辄 100 GB – 几 TB，而昇腾 A5 单卡 HBM 容量 64–80 GB，**装不下**。

**现有方案（缺陷）**：
- **方案 A：手动 sharding**——把一张大表拆成 N 段，每段放一张卡
  - **缺陷 1**：必须改 FBGEMM 的 `EmbeddingLocation` 配置 + 写 key-routing 逻辑
  - **缺陷 2**：跨段访问要走 HCCL 通信，**性能下降 30–50%**
  - **缺陷 3**：客户需要熟悉 FBGEMM 内部实现，**迁移成本高**
  - **缺陷 4**：torchrec-ascend 大量代码是 sharding 相关，改动巨大
- **方案 B：手动 H2D copy**——把表放 CPU DRAM，每次 batch 显式 copy
  - **缺陷 1**：每次访问都要 copy，PCIe 带宽打满
  - **缺陷 2**：延迟不可接受（> 100ms / batch）
  - **缺陷 3**：与 FBGEMM `EmbeddingLocation.HOST` 路径匹配，但需要业务方自己管理缓存策略

#### 4.2.2 FBGEMM 三方库适配"卡在 UVM"

**问题**：FBGEMM 的 4 种 `EmbeddingLocation`（`DEVICE` / `MANAGED` / `MANAGED_CACHING` / `HOST`），其中：
- `DEVICE` 昇腾 ✅ 已支持
- `HOST` 昇腾 ✅ 已支持
- `MANAGED` 昇腾 ❌ 无对应
- `MANAGED_CACHING` 昇腾 ❌ 无对应

**后果**：客户在 NVIDIA 上跑通的 `MANAGED_CACHING` 性能调优配置，到昇腾上**只能改用 `DEVICE` 或 `HOST`**，业务代码不变但**性能下降 50%+**。

**具体受影响代码**（详见 [FBGEMM_UVM分析报告.md §3.3](FBGEMM_UVM分析报告.md#33-算子-文件对照表)）：
- [`split_table_batched_embeddings_ops_inference.py:1625`](fbgemm_gpu/fbgemm_gpu/split_table_batched_embeddings_ops_inference.py#L1625) `else: weights = self.weights_uvm` 这条分支在昇腾上**无法走到**
- [`split_table_batched_embeddings_ops_training.py:357-401`](fbgemm_gpu/fbgemm_gpu/split_table_batched_embeddings_ops_training.py#L357) `if split.uvm_size > 0` 这个分支永远不进
- [`lxu_cache.cu:84-145`](fbgemm_gpu/src/split_embeddings_cache/lxu_cache.cu#L84) `lxu_cache_flush_cuda` 写回 UVM 的功能在昇腾上**未实现**
- [`test/tbe/cache/cache_test.py:405`](fbgemm_gpu/test/tbe/cache/cache_test.py#L405) `tbe.total_uvm_usage` 事件**上报不到**
- [`test/faster_hash_test.py:668-693`](fbgemm_gpu/test/faster_hash_test.py#L668) `test_zch_output_on_uvm` 测试**跑不了**

#### 4.2.3 与 FBGEMM-Ascend 项目的"差距"联动

> 🟢 **本节内容全部可由本仓库源码 / git log 一手验证**。"未迁移清单"中每一项对应 [FBGEMM_UVM分析报告.md §3.3](FBGEMM_UVM分析报告.md#33-算子-文件对照表) 的 FBGEMM 源码行号。

### 5.2 产品价值

#### 5.2.1 战略价值

- **拿下搜广推市场入场券**：UVM 是 FBGEMM/TorchRec 的事实依赖，**不补 UVM 等同于把搜广推开源生态拒之门外**
- **互联网客户拓展的"硬技术门槛"**：搜广推是互联网公司 AI 算力第一大场景，打下它就拿下 60% 互联网 AI 算力市场
- **NVIDIA UVM 8 年护城河的对位**：昇腾 950 是迎头赶上的关键代际

#### 5.2.2 商业价值

> 🔴 **本节所有数字（100 亿美元、60%、20-30%、12-18 亿美元等）均为 AI 粗估，无第三方报告或商务团队一手数据支撑。** 必须由商务/BU/财务团队 M1 核实后方可用于对外材料。

#### 5.2.3 技术价值

- **统一抽象层**：`aclrtMallocManaged` 系列 API 补齐后，CANN 内存子系统的能力对齐 CUDA
- **生态反哺**：UVM 补齐后，多个三方库可"零成本"适配（FBGEMM → TorchRec → HSTU → vLLM 部分场景）
- **MoE 场景铺垫**：GenAI MoE 专家权重稀疏激活 + 100+ GB 专家库 = 天然的 UVM 用例；950 时代打好 UVM 基础，MoE 时代自然受益
- **跨代际价值**：UVM 一旦补齐，950 → 960 → 970 持续受益

### 5.3 技术价值（详细）

- **page fault 机制补齐**：昇腾软件栈首次具备硬件级"按需分页"能力
- **HCCL 协同**：UVM 跨卡 / 跨节点迁移可与 HCCL 集合通信协同优化
- **CANN 内存管理升级**：从"显式分配"到"声明意图"（`aclrtMemAdvise`），简化用户编程
- **大页支持**：2 MB 大页机制配套，可减少 30-50% page fault 开销
- **可观测性**：6 项 UVM cache 统计 + Profiler 集成，让调优有据可依
- **可移植性**：同一份 FBGEMM-Ascend 代码在 950PR/DT/DT POD 三种形态通用

### 5.4 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 性能不达预期（< 0.85× 竞品） | 中 | 客户体验差 | 仿 FBGEMM 两步 advise + 大页 + 与 HCCL 协同预取 |
| PCIe/RoCE 带宽瓶颈 | 高 | 多卡场景吞吐受限 | 优化迁移粒度（2 MB 大页）+ 主动预取 |
| 跨节点一致性难 | 中 | POD 形态推迟 | Phase 1/2 先做 950PR/DT，Phase 3 做 POD |
| 客户实际模型超 FBGEMM benchmark | 中 | benchmark 通过但客户场景失败 | 收集 5+ 头部客户典型模型作为回归测试集 |
| FBGEMM 上游 API 变更 | 低 | 维护成本 | 锁版本 v1.5.0-release，季度同步上游 |

### 5.5 价值总览（一句话）

> **本需求在昇腾 950 系列上提供与 NVIDIA UVM 功能对等的统一内存能力，使 FBGEMM / TorchRec 等搜广推事实标准三方库可"零修改"运行在昇腾 NPU 上，**直接解决客户推荐系统 embedding 表"装不下、性能差、迁移慢"三大痛点**，以 950PR / 950DT / 950DT POD 三种形态覆盖单卡 / 单机多卡 / 跨节点集群全场景，是昇腾打入搜广推 / 互联网市场的关键技术入场券。**

- 🟢 "提供与 NVIDIA UVM 功能对等的能力" — 基于 FBGEMM UVM API 已完全识别（[FBGEMM_UVM分析报告.md](FBGEMM_UVM分析报告.md)）+ 差距清单（§4.1）
